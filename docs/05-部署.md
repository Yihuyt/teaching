# 部署

本文说明如何在服务器上部署整套系统。所有服务运行在 Docker 中，由 `deploy/compose.yaml` 编排。本机开发见 [本地开发](01-本地开发.md)，代码结构见 [架构](02-架构.md)。

以下命令均在仓库根目录执行。

## 服务组成

| 服务 | 职责 | 镜像 | 所在网络 |
|---|---|---|---|
| `frontend` | 前端页面，并将 `/api` 转发给后端、`/scratch` 转发给积木编辑器 | 由 `deploy/docker/frontend/Dockerfile` 构建 | edge |
| `backend` | 业务后端 | 由 `deploy/docker/server/Dockerfile` 构建 | edge、data |
| `judge-worker` | 判题进程，内置 go-judge 沙箱和 GCC 13、G++ 13、Python 3.12 | 由 `deploy/docker/judge-worker/Dockerfile` 构建 | judge |
| `scratch-editor` | 积木编辑器 | 由 `deploy/docker/scratch-editor/Dockerfile` 构建 | edge |
| `mysql` | 数据库 | 官方 `mysql:8.4.6` | data |
| `redis` | 登录会话、登录失败计数、判题任务队列 | 官方 `redis:8.2.7-alpine` | data、judge |
| `elasticsearch` | 知识库检索 | 官方 `elasticsearch:9.5.1` | data |

容器分布在三个 Docker 内部网络中，同一网络内的容器可以互相访问，不同网络之间互相隔离：

- **data**：封闭网络，既不能访问外网，也无法从外部连入。MySQL、Redis、Elasticsearch 只在此网络中，后端同时接入此网络和 edge 网络。
- **edge**：可访问外网。前端在此接收浏览器的请求，后端经此访问 OSS、大模型和 MinerU。
- **judge**：只有判题进程和 Redis。判题进程从 Redis 领取任务、从 OSS 下载测试数据，无法访问数据库和后端。

对外开放的端口是 `deploy/.env` 中的 `WEB_PORT`（默认 8067），映射到前端容器；其他服务没有对外端口。

数据卷（Compose 会加上项目名前缀，如 `teaching-platform_mysql_data`）：

| 数据卷 | 内容 |
|---|---|
| `mysql_data` | 全部业务数据 |
| `redis_data` | Redis 持久化文件（开启 appendonly） |
| `es_data` | 知识库检索索引 |
| `testcase_cache` | 判题进程从 OSS 下载的测试数据缓存，保留 7 天 |

课程资料、图片、视频、判题测试数据都存放在阿里云 OSS，不在服务器上。

## 服务器要求

- Linux，CPU 架构为 amd64 或 arm64（判题镜像中的 go-judge 只提供这两种）。
- Docker Engine 23 或更高版本及 Compose 插件。镜像构建使用了 BuildKit 的缓存挂载，Docker 23 起默认启用。
- 判题进程以 `privileged: true` 运行，这是 go-judge 沙箱的要求；不允许特权容器的环境（如部分云容器服务）无法运行判题进程。
- 内存和 CPU 上限：

| 服务 | 默认上限 | 在 `deploy/.env` 中调整 |
|---|---|---|
| 后端 | 内存 6 GB | `BACKEND_MEMORY` |
| 判题进程（每个副本） | 2 个 CPU、内存 2 GB | `JUDGE_WORKER_CPUS`、`JUDGE_WORKER_MEMORY` |
| Elasticsearch | 未设上限；堆内存 512 MB，容器整体约 1.5 GB | — |
| MySQL、Redis、前端、积木编辑器 | 未设上限 | — |

  按默认值合计接近 10 GB，另需为 MySQL 和系统预留余量。

- 网络：
  - 构建镜像时需能访问 Docker Hub、Maven 中央仓库、npm 仓库、Ubuntu 软件源和 GitHub（下载 go-judge）。无法访问时见「离线部署」一节。
  - 运行时，后端需能访问 OSS、`dashscope.aliyuncs.com`（大模型）和 `mineru.net`（文档解析），判题进程需能访问 OSS。
  - 浏览器上传和查看文件时直接访问 OSS，师生所在网络也需能访问 OSS。

## 首次部署

### 1. 获取代码

将仓库克隆或复制到服务器，进入仓库根目录。

### 2. 准备密码和密钥

在 `deploy/secrets/` 下准备以下 7 个文件，生成命令和 OSS 密钥的格式见 [本地开发](01-本地开发.md) 第 1 步，各文件的用途见 `deploy/secrets/README.md`：

`mysql-root-password`、`mysql-app-password`、`redis-password`、`elastic-password`、`root-initial-password`、`ai-config-key`、`aliyun-oss-credentials`

- 文件权限均为 `600`。缺少任一文件，对应容器拒绝启动；MySQL 和 Redis 的密码还必须是 48 位 Base64，否则同样无法启动。
- MySQL 和 Elasticsearch 的密码在首次启动时写入数据卷，此后修改文件不会改变已有数据的密码，反而会导致后端和健康检查连接失败。
- `root-initial-password` 只在 root 尚未设置自己的密码时使用。
- `ai-config-key` 用于加密教师保存的大模型密钥和 MinerU 令牌。投入使用后不得更换，更换后已保存的密钥无法解密，所有人需要重新填写。

### 3. 填写 deploy/.env

```bash
cp deploy/.env.example deploy/.env
```

| 配置项 | 含义 |
|---|---|
| `COMPOSE_PROJECT_NAME` | Compose 项目名，保持 `teaching-platform` |
| `WEB_PORT` | 对外开放的端口，访问地址为 `http://服务器地址:WEB_PORT/` |
| `ALIYUN_OSS_ENDPOINT` | OSS 地域节点，填写完整的 `https://` 地址 |
| `ALIYUN_OSS_RESOURCE_BUCKET` | 存放课程资料的 bucket |
| `ALIYUN_OSS_TESTCASE_BUCKET` | 存放判题测试数据的 bucket |
| `SESSION_COOKIE_SECURE` | 登录 Cookie 是否仅限 HTTPS 发送。以 HTTP 访问时保持 `false`，启用 HTTPS 后改为 `true` |
| `JUDGE_WORKER_CONCURRENCY` | 每个判题进程同时评测的提交数，默认 1 |
| `JUDGE_WORKER_CPUS`、`JUDGE_WORKER_MEMORY` | 每个判题进程的 CPU 和内存上限，默认 2 个 CPU、2 GB |
| `BACKEND_MEMORY` | 后端的内存上限，默认 6 GB |

后四项在 `.env.example` 中被注释，不修改则使用默认值。

### 4. 配置 OSS 跨域规则

规则见 [本地开发](01-本地开发.md) 第 3 步，区别在于来源须为师生实际访问的地址，如 `http://192.168.1.10:8067` 或 `https://teaching.example.edu.cn`。一个 bucket 可以配置多条来源，开发用的 `http://localhost:8067` 可与服务器地址并存。

### 5. 构建并启动

```bash
docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml up -d --build
```

后端镜像构建时会运行后端全部测试，测试不通过则镜像构建失败，因此首次构建耗时较长。

### 6. 确认启动成功

```bash
docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml ps
```

七个服务均为 `(healthy)` 即启动完成。前端在后端健康后才启动。随后访问 `http://服务器地址:WEB_PORT/`。

### 7. 首次登录

用户名 `root`，密码为 `deploy/secrets/root-initial-password` 的内容，首次登录后必须修改密码，之后在「账户管理」中创建管理员、教师和学生账户。AI 功能所需密钥的配置见 [课程与权限](04-业务说明/03-课程与权限.md)。

### 8. 防火墙

只放行 `WEB_PORT`。

## 离线部署

服务器无法访问 Docker Hub、GitHub 等地址时，在可联网的机器上构建镜像后传到服务器，两台机器的 CPU 架构必须相同。

在可联网的机器上，准备好仓库、`deploy/.env` 和 `deploy/secrets/` 后执行：

```bash
docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml build
docker pull mysql:8.4.6 && docker pull redis:8.2.7-alpine && docker pull elasticsearch:9.5.1
docker save teaching-platform-frontend teaching-platform-backend teaching-platform-judge-worker \
  teaching-platform-scratch-editor mysql:8.4.6 redis:8.2.7-alpine elasticsearch:9.5.1 \
  | gzip > teaching-images.tar.gz
```

将 `teaching-images.tar.gz` 传到服务器，在服务器的仓库根目录执行：

```bash
gunzip -c teaching-images.tar.gz | docker load
docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml up -d --no-build
```

服务器上仍需完整的仓库：MySQL 的初始化脚本、建表脚本和中间件的启动脚本都从仓库挂载进容器。

## 日常操作

下表中 `<compose>` 代表 `docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml`。

| 操作 | 命令 |
|---|---|
| 查看状态 | `<compose> ps` |
| 停止全部服务 | `<compose> stop` |
| 启动全部服务 | `<compose> up -d` |
| 重启某个服务 | `<compose> restart backend` |
| 修改 `deploy/.env` 后使其生效 | `<compose> up -d`（`restart` 不会重新读取 `.env`） |
| 停止并删除容器（保留数据） | `<compose> down` |

**`down -v` 会删除包括数据库在内的全部数据卷。**

所有服务均设置了 `restart: unless-stopped`。Docker 服务开机自启（`systemctl enable docker`）时，服务器重启后系统自动恢复。

## 日志

后端和判题进程将日志写入仓库根目录的 `logs/`：

| 服务 | 日志文件 |
|---|---|
| 后端 | `logs/backend/backend.log` |
| 判题进程 | `logs/judge-worker/judge-worker.log` |

文件按天切分，单个文件超过 50 MB 时再切分；保留 30 天，总量超过 1 GB 时删除最旧的文件。

各服务的控制台输出可用 `<compose> logs 服务名` 查看，每个容器最多保留 5 个 50 MB 的文件。

页面错误提示末尾的「错误编号 xxxxxxxx」出现在日志每行级别后的方括号中，按编号检索即可找到该请求的全部记录：

```bash
grep 'xxxxxxxx' logs/backend/backend*.log
```

所有容器使用 UTC 时间，日志时间比北京时间晚 8 小时。

## 备份与恢复

需要备份的：

- **MySQL**：全部业务数据，应定期备份。
- **`deploy/secrets/` 和 `deploy/.env`**：单独妥善保存。其中 `ai-config-key` 一旦丢失，库中保存的 AI 密钥将无法解密。

无需在服务器上备份的：

- **OSS 上的文件**：课程资料、图片、视频、测试数据存放在阿里云。
- **Elasticsearch**：只是检索副本，知识库正文在 MySQL 中。索引丢失时在各知识库页面执行「重建索引」即可恢复，重建会重新向量化，消耗课程负责人的模型额度。
- **Redis**：存放登录会话、登录失败计数和判题任务队列。

备份 MySQL（密码在容器内读取，不出现在命令行和终端历史中）：

```bash
docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml exec -T mysql \
  sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql-root-password)" mysqldump -uroot --single-transaction --routines --triggers teaching_platform' \
  | gzip > teaching_platform-$(date +%F).sql.gz
```

恢复前先停止后端，恢复后再启动：

```bash
docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml stop backend
gunzip -c teaching_platform-2026-10-01.sql.gz | docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml exec -T mysql \
  sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql-root-password)" mysql -uroot teaching_platform'
docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml start backend
```

## 升级

1. 按上一节备份 MySQL。
2. 获取新代码：`git pull`，或用新代码覆盖仓库。
3. **新版本修改了表结构时，先修改数据库。** `schema.sql` 只在 MySQL 首次初始化时执行，已有数据库不会自动更新，需在库上手工执行对应的 `ALTER`。后端连库所用账户只有增删改查权限，须以 MySQL root 执行：

   ```bash
   docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml exec -T mysql \
     sh -c 'MYSQL_PWD="$(cat /run/secrets/mysql-root-password)" mysql -uroot teaching_platform' < 变更.sql
   ```

4. 重新构建并启动：

   ```bash
   docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml up -d --build
   ```

   前端、后端、判题进程都从当前代码构建，同时更新。有变化的服务会被重新创建，数据卷不受影响。

## 增加判题进程

提交较多、判题排队时，可增加判题进程副本，各副本共同从 Redis 领取任务：

```bash
docker compose -p teaching-platform --env-file deploy/.env -f deploy/compose.yaml up -d --scale judge-worker=3
```

- 每个副本的并发评测数、CPU 和内存上限分别由 `JUDGE_WORKER_CONCURRENCY`、`JUDGE_WORKER_CPUS`、`JUDGE_WORKER_MEMORY` 设置，总资源占用为副本数乘以单个副本的上限。
- 各副本运行在同一台服务器上。
- 各副本共用 `logs/judge-worker/` 目录，写入同一个日志文件 `judge-worker.log`。

## 启用 HTTPS

系统本身只提供 HTTP。启用 HTTPS 需在前面加一层负责证书的反向代理（如学校已有的 Nginx 或负载均衡），由它将请求转发到 `WEB_PORT`，然后：

1. 在 `deploy/.env` 中将 `SESSION_COOKIE_SECURE` 改为 `true`，执行 `<compose> up -d`。
2. 让登录限流取得用户的真实 IP。前端容器的 Nginx 目前只信任直接连入的地址，加了前置代理后，所有请求的来源地址都变为代理地址，同一 IP 登录失败 30 次将锁定所有用户。需修改 `deploy/docker/frontend/nginx.conf`，在 `server` 块中只信任前置代理传来的地址：

   ```nginx
   set_real_ip_from 前置代理的地址;
   real_ip_header X-Forwarded-For;
   ```

   修改后执行 `<compose> up -d --build frontend`。
3. 将 OSS 跨域规则的来源改为 `https://` 开头的实际地址。
4. 防火墙只允许前置代理访问 `WEB_PORT`。

## 安全要点

- `deploy/secrets/` 下的文件权限均为 `600`，`.gitignore` 已将它们和 `deploy/.env` 排除在 Git 之外。
- 对外只开放 `WEB_PORT`。MySQL、Redis、Elasticsearch 位于内部网络，没有对外端口；后端的健康检查地址（`/actuator`）不经过前端 Nginx，外部无法访问。
- 判题进程是特权容器，学生提交的代码在其中的 go-judge 沙箱内运行。

## 常见问题

- **某个服务长时间未变为 `healthy`：** 用 `<compose> logs 服务名` 查看原因。缺少密钥文件或密码格式不对时，日志中会有「缺少有效的容器 secret」「必须是 48 位 Base64 值」等提示。
- **修改 MySQL 或 Elasticsearch 的密码文件后服务无法启动：** 这两项密码在首次启动后已固定在数据卷中，需改回原密码。
- **`WEB_PORT` 被占用：** 前端容器启动失败，在 `deploy/.env` 中更换端口，或停止占用端口的程序。
- **Elasticsearch 无法启动或被系统终止：** 容器整体约需 1.5 GB 内存，先检查服务器内存。日志提示 `vm.max_map_count` 过小时，在宿主机执行 `sysctl -w vm.max_map_count=262144`，并写入 `/etc/sysctl.conf` 使其重启后仍生效。
- **启动日志中有 OSS 的 `AccessDenied` 警告：** 属正常现象，说明见 [本地开发](01-本地开发.md) 的「常见问题」。
- **判题进程无法启动：** 依次检查：
  - 宿主机是否允许特权容器；
  - `deploy/secrets/aliyun-oss-credentials` 是否正确；
  - `deploy/.env` 中的 OSS 地址和测试数据 bucket 是否正确，日志出现「判题测试数据 OSS bucket 不存在或当前凭据无权访问」即说明这两项有误；
  - Redis 是否为 `healthy`。
- **上传文件失败：** 检查 OSS 跨域规则的来源是否与浏览器地址栏中的地址完全一致，包括 `http`/`https` 和端口。
