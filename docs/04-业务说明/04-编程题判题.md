# 编程题判题

学生提交代码后，系统编译运行并逐个测试点比对输出，给出评测结果。本文说明一次提交从写入到出结果的过程。

代码分三处：业务后端的 `programming` 模块（`backend/server/src/main/java/cn/utcy/teaching/programming/`）负责题目、提交和结果；独立进程 `backend/judge-worker` 在 go-judge 沙箱中编译运行；`backend/judge-contract` 定义两边共用的测试数据包格式。后端与判题进程之间通过 Redis Stream 通信。

## 整体流程

```text
学生提交
  → SubmissionApplicationService.submit：同一事务写入提交记录（QUEUED）和判题作业（pending）
        │
JudgeJobPublisher（定时）→ 把作业写入 Redis Stream「judge.jobs」→ 作业改为 published
        │
判题进程 JudgeStreamWorker 以消费者组领取任务
  → 从 OSS 下载测试包（本地缓存）
  → EvaluationEngine：go-judge 编译 → 逐个测试点运行 → 比对输出
  → 写入结果流「judge.results」并确认任务
        │
后端 JudgeResultListener（定时）读取结果流
  → JudgeResultApplicationService.complete：校验、保存提交与测试点结果
        │
JudgeJobReconciler（定时）：以数据库为准对账，超时未出结果的作业重新发布
```

## 主流程

### 1. 题目与测试数据

题目保存在 `programming_problem`。判分用的测试点打包成 zip 测试包，存放在 OSS 的测试数据 bucket，题目上只记录测试包的 SHA-256；测试包的对象键由题目编号和 SHA-256 组成，测试数据修改后对象键随之改变。测试包可以由教师手工填写生成，也可以从标准题目包导入。

### 2. 提交

学生提交时，后端在同一事务中写入提交记录和一条判题作业（`judge_job`）：

```java
// backend/server/src/main/java/cn/utcy/teaching/programming/application/SubmissionApplicationService.java
Actor actor = currentActor.require();
ProgrammingSubmission submission = ProgrammingSubmission.create(
        problem.getId(), actor.userId(), language, sourceCode);
requireMutation(submissions.insert(submission), "提交记录创建未生效");
requireMutation(jobs.insert(JudgeJob.pending(submission.getId())), "判题任务创建未生效");
return view(submission, problem);
```

作业以数据库为准，Redis 中的任务丢失时可由作业重新发布。作业的 `attempt` 表示第几次执行，每次重新发布都加 1。

### 3. 发布到 Redis

`JudgeJobPublisher` 定时取出待发布的作业，由 `JudgeJobPublicationExecutor` 把任务（题目限制、测试包哈希、源代码）写入 Stream `judge.jobs`，之后作业改为 `published`。写入通过 Lua 脚本按「作业编号:attempt」去重，同一次执行重复发布时 Stream 中只有一条记录。

### 4. 判题进程领取任务

判题进程 `judge-worker` 的 `JudgeStreamWorker` 以消费者组 `judge-workers` 从 `judge.jobs` 领取任务，可以部署多个副本共同领取。正在评测的任务会定期续租；某个副本崩溃后，它领取的任务在租约到期后由其他副本接管。

### 5. 编译与运行

`TestcasePackageStore` 先查本地缓存，缺失时从 OSS 下载测试包并校验 SHA-256。`EvaluationEngine` 通过 `GoJudgeClient` 调用同一容器内的 go-judge：先编译一次（C17、C++20 编译，Python 3.12 做语法检查），编译失败直接返回 `COMPILE_ERROR`；然后逐个测试点运行、比对输出，总结果取第一个未通过测试点的结果：

```java
// backend/judge-worker/src/main/java/cn/utcy/teaching/judge/sandbox/EvaluationEngine.java
for (TestcasePackage.Testcase testcase : testcasePackage.cases()) {
    JudgeCaseResult result = runCase(job, compile, testcase);
    caseResults.add(result);
    totalTimeMs = Math.addExact(totalTimeMs, result.timeUsedMs());
    peakMemoryKb = Math.max(peakMemoryKb, result.memoryUsedKb());
    score = score.add(result.score());
    if (overall == JudgeStatus.ACCEPTED && result.status() != JudgeStatus.ACCEPTED) {
        overall = result.status();
    }
}
```

比对前统一换行符，去掉行尾空白和末尾空行。

### 6. 写回结果

`AtomicResultPublisher` 用一个 Lua 脚本同时完成两件事：把结果写入 `judge.results`，并确认（`XACK`）这条任务。任务已被后端对账回收时脚本拒绝写入，执行过慢的判题进程提交不了已作废的结果。

### 7. 后端保存结果

`JudgeResultListener` 定时读取 `judge.results`，每条结果交给 `JudgeResultApplicationService.complete`。结果的 `attempt` 与作业当前的 `attempt` 不一致时丢弃，防止旧执行的结果覆盖新结果：

```java
// backend/server/src/main/java/cn/utcy/teaching/programming/application/JudgeResultApplicationService.java
if (job.getAttempt() != result.attempt()) {
    return new Completion(CompletionOutcome.STALE_ATTEMPT, null);
}
```

校验通过后，提交改为终态，写入各测试点结果，作业改为 `completed`，并记录学情事件。无法应用的结果写入死信表 `judge_result_dead_letter`，后面的结果继续处理；死信可在「平台设置」中重放或丢弃。

### 8. 对账与重判

`JudgeJobReconciler` 定时以数据库为准对账：已发布但超时未出结果的作业，回收 Redis 中的旧投递，`attempt` 加 1 后重新发布，重新发布次数用完则判为 `SYSTEM_ERROR`；长时间未能发布的作业也判为 `SYSTEM_ERROR`。

教师重判一份提交或一道题时，与对账使用同一个复位方法，把作业改回待发布、`attempt` 加 1，然后走同样的发布流程。

## 评测结果

| 结果 | 含义 |
|---|---|
| `QUEUED` | 等待评测 |
| `ACCEPTED` | 全部测试点通过 |
| `WRONG_ANSWER` | 输出与标准答案不一致 |
| `COMPILE_ERROR` | 编译失败（Python 为语法检查失败） |
| `RUNTIME_ERROR` | 非零退出、被信号终止或调用被禁止的系统调用 |
| `TIME_LIMIT_EXCEEDED` | 超时 |
| `MEMORY_LIMIT_EXCEEDED` | 超内存 |
| `OUTPUT_LIMIT_EXCEEDED` | 输出超限 |
| `SYSTEM_ERROR` | 评测系统自身出错 |
| `WORKER_CRASH_LIMIT` | 判题进程多次未能完成该提交 |
