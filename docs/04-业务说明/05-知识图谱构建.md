# 知识图谱构建

知识图谱是一门课的知识结构。图谱有两种来源：教师在编辑器中手工编辑，或者从一本 PDF 教材自动构建。本文主要说明教材构建是怎样完成的。

后端在 `backend/server/src/main/java/cn/utcy/teaching/knowledgegraph/`，前端在 `frontend/src/features/knowledgegraph/`，提示词在 `backend/server/src/main/resources/knowledgegraph/prompts/`。下文省略这些前缀。大模型调用见 [大模型基础组件](01-大模型基础组件.md)，后台任务的运行机制见 [长任务与实时推送](02-长任务与实时推送.md)。

## 整体流程

```text
资料库中的 PDF 教材
   ↓  KnowledgeGraphBuildService.create：建立构建记录，交给后台执行
MinerU 解析成逐页文本
   ↓
识别目录：找目录页 → 解析目录条目 → 校准页码
   ↓
教师在向导中核对、修改目录 → 按目录切分抽取小节
   ↓
各小节并行抽取知识点和关系（GraphExtractionService）
   ↓
合并修复：合并重复的知识点、去掉前置关系中的环、装配成预览
   ↓
教师命名后入库，生成一张新图谱
```

## 图谱的结构

图谱由三类节点组成一棵树：章节下可以放章节和知识点，知识点下可以放代码示例。知识点之间另有两种关系：「前置」表示学习先后，「相关」表示内容关联。节点上可以挂课程里的文件、试题和编程题。

所有写入，包括编辑器中的每个操作和构建入库，都经过 `domain/GraphRules` 校验。父子能否组合由 `canContain` 判定，`parent` 为 `null` 表示图谱根：

```java
// backend/server/src/main/java/cn/utcy/teaching/knowledgegraph/domain/GraphRules.java
public static boolean canContain(NodeKind parent, NodeKind child) {
    if (parent == null || parent == NodeKind.UNIT) {
        return child == NodeKind.UNIT || child == NodeKind.KNOWLEDGE_POINT;
    }
    if (parent == NodeKind.KNOWLEDGE_POINT) {
        return child == NodeKind.CODE_EXAMPLE;
    }
    return false;
}
```

`GraphRules` 还规定关系只能连接两个知识点、前置关系不能成环。

手工编辑的页面是 `views/AdminKnowledgeGraphEditorView.vue`。每个操作即时提交，后端 `application/KnowledgeGraphEditor` 锁住图谱、校验后写入，再返回整张图谱，前端用它替换本地状态。

## 教材构建

### 1. 解析教材

`application/KnowledgeGraphBuildService.create` 检查资料是已上传的 PDF、课程负责人已配置密钥，然后建立构建记录，交给 `KnowledgeGraphBuildPipeline` 在后台执行。

后台先调用 `MineruClient.parseToPages` 取得逐页文本。教材构建使用逐页文本，因为目录确认、按页切分小节和知识点出处都依赖准确的页码。

### 2. 识别目录

`application/TocRecognitionService.recognize`：

```java
// backend/server/src/main/java/cn/utcy/teaching/knowledgegraph/application/TocRecognitionService.java
List<Integer> tocPages = detectTocPages(apiKey, pages, onProgress);
List<String> notes = new ArrayList<>();
if (!tocPages.isEmpty()) {
    onProgress.accept("发现目录页 " + tocPages + ",正在解析目录…");
    List<ParsedEntry> parsed = parseTocPages(apiKey, pages, tocPages);
    List<TocEntry> aligned = alignPages(parsed, pages, tocPages, notes);
    double accuracy = verifyAndFix(aligned, pages, notes);
```

- 找目录页：对教材前面的若干页，由模型判断哪些是目录页（`toc-detect`）。
- 解析目录：把目录页文本交给模型解析成条目（`toc-parse`）。
- 校准页码：目录上印的是书页码，与 PDF 的物理页码有偏移。`alignPages` 在正文中查找各条标题实际出现的页，统一校准偏移，`verifyAndFix` 再逐条核对。
- 找不到目录页或核对结果不理想时，改用 `TocCandidateExtractor` 按正文中的「第X章」「X.Y」等编号提取目录。

### 3. 确认目录，切分小节

目录决定整张图谱的章节结构，因此由教师在构建向导中核对和修改（`components/build/TocEditor.vue`）。确认后，`KnowledgeGraphBuildService.saveToc` 用 `SectionSlicer` 按目录的末级条目切分小节，每个小节取对应页码范围内的文本，过长的再分成几片。

重新确认目录时，标题和页码范围都没有变化的小节保留已有的抽取结果，只有受影响的小节重新抽取。

### 4. 并行抽取

`GraphExtractionService.extractSections` 并行处理各小节：先用 `summarize` 提示词生成本节摘要，再把摘要和原文交给 `kg-extract`，输出本节的知识点、关系和代码示例。每个小节完成后立即保存。

某些小节失败时，教师可以只重新抽取失败的小节，也可以忽略它们直接进入合并。

### 5. 合并修复

同一个知识点会在多个小节中重复出现，名称也不完全一致。`GraphExtractionService.finalizeGraph` 把各小节的结果合成一张图：

```java
// backend/server/src/main/java/cn/utcy/teaching/knowledgegraph/application/GraphExtractionService.java
List<String> warnings = new ArrayList<>();
List<EntityMerger.CandidatePair> candidates = new ArrayList<>(merger.exactMergeAndCollectCandidates());
candidates.addAll(semanticCandidates(apiKey, merger, candidates, warnings));
if (!candidates.isEmpty()) {
    onStage.accept("有 " + candidates.size() + " 对相似知识点，正在裁决是否合并…");
    adjudicate(apiKey, candidates, cancelled).forEach(merger::applyMerge);
}
EntityMerger.MergeResult mergeResult = merger.finalizeMerge();
```

1. 名称相同的知识点直接合并（`domain/EntityMerger`）。
2. 名称相似、别名重叠或释义的向量相近的知识点对列为候选，交给模型（`entity-merge`）判断是否合并。
3. 关系端点改写为合并后的名称；`domain/GraphRepairer` 去掉前置关系中的环。
4. 按层级由深到浅汇总出各章节的摘要。
5. `domain/GraphAssembler` 装配成预览：目录条目成为章节节点，知识点挂在首次出现的小节下，代码示例挂在对应的知识点下。

### 6. 入库

教师查看预览并为图谱命名后，`KnowledgeGraphBuildService.complete` 在一个事务中新建图谱，依次写入节点和关系，并按 `GraphRules` 对整张图复核，随后删除构建记录。入库后的图谱与普通图谱相同，可以在编辑器中继续修改。

构建在后台运行，教师离开页面后仍继续，回到向导可以查看进度。后端重启或长时间没有进展时，构建被判为失败；重试时从断点继续，已解析的文本和已完成的小节都保留。
